Your stated goal

Solid underlying data model first; views (taskbar, shortcuts, frames) should be replaceable. Today the taskbar path is closest. Frames and shortcuts are still Swing-first, with AppStore as a growing shadow of DesktopManager rather than the single source of truth.

Strengths

Catalog S1

JSON-driven registration (vapps-config / external-apps) keeps the tool roster out of Java hardcoding.

Launch pipeline S2

DesktopAction → (new Spec) → DesktopManager.createVApp is a clear create path for menus and shortcuts.

Taskbar S3

WindowListView is a real view interface; JList vs SmartGrid swap without touching Redux or controller logic.

State shapes S4

ToolInstance / ToolsState / WindowListState are immutable and copy-on-write — right shape for a solid model.

Vocabulary S5

GLOSSARY.md + CLAUDE.md give consistent names (tool/vapp, Spec, Frame, DockingWorkspace).

External apps S6

LaunchAware / ExternalAppSpec keep process launch as a variant of the same create path.

Highest-impact leaks (detail)

W1 — Dual registry

DesktopManager keeps EventList<VirtualAppFrame> and is still what activates/closes frames. AppStore is updated from InternalFrameListener callbacks. WindowListController rebuilds a frameCache from DesktopManager on every state change so the view can act on real frames. Swappable taskbar views sit on top of a non-swappable Swing registry.

W2 — Spec is not a recipe

VirtualAppSpec holds title/icon flags and the content JPanel, a DockingWorkspace, a static DockingService, and dockable ID bookkeeping. The glossary calls Spec a descriptor; the class is also a mini controller for docking. That blocks treating Spec as serializable/pure model.

W3 — Fragmented identity

Frame: UUID toolId. Grouping: Spec simple name as toolType. Docking: title-derived dockableId. Store open: workspaceId = null. Location events: CLocation toString(). Joining “this tool’s panel moved to that frame’s workspace” requires ad-hoc string matching.

Docking (separate track — fundamental to the product)

Docking started as a complicated add-on and shows a cleaner library boundary than ownership model. For this desktop’s goals it is not “optional chrome”: every open tool’s content is a dockable unit; hosts (frames / workspaces) are temporary placement. A tool that never leaves its opening container is the degenerate special case that may look like “no docking” to users. The analysis below still treats docking separately because of SPI/implementation complexity — not because it is optional to the paradigm.

Piece Status Note
SPI surface Good DockingService / DockingProvider / Dockable / DockingWorkspace abstract Bibliothek well.
Ownership Leaky VirtualAppSpec implements ToolSpec; DockingSession on VirtualAppFrame owns workspace by toolId.
isDockable() Stub Always returns true — accidentally aligned with “docking is fundamental,” but not designed as a product rule yet.
Redux DockingState Partial Model exists; TOOL_OPENED passes workspaceId=null; PANEL_LOCATION_CHANGED mostly logs.
ID bridge Weak Dockable IDs from titles; toolIds are UUIDs. Cross-frame dock tracking and future close-by-content cannot cleanly join them.
Impl cast Leak VirtualAppSpec casts DockingService → DockingServiceImpl to get provider for builders.
Recommended framing for docking work

Keep the SPI. Move workspace ownership off Spec onto a toolId-scoped session (beside the host layer). Make dockableId == toolId (or a stable child id under toolId). Treat hosts as temporary: a content realizer (toolId → panel/dockable + current host) should back close/move — closing disposes content wherever it lives, not necessarily the opening frame. Only then deepen Redux DockingState — otherwise the model will keep mirroring incomplete events.

SpecDocking escape hatch

SpecDocking talks to native Bibliothek CControl directly — an intentional demo leak past the SPI. Do not treat it as the pattern for production tools.

Goal vs reality

Closest to the goal

Taskbar: Redux state → controller → WindowListView. Views are replaceable; grouping logic stays out of the view.

Catalog JSON: declarative list of what exists to launch.

Immutable ToolInstance: good target shape for “one open tool.”

Still Swing-first

Open windows: DesktopManager + VirtualAppFrame are authoritative.

Shortcuts: VShortcut JLabel; no position/selection model.

Actions: Swing Action is the catalog object, not a pure command DTO.

Suggested consolidation order (no code yet)

  1. Pick one registry for open tools — prefer AppStore as source of truth; DesktopManager becomes a “realizer” that creates/destroys frames from toolOpened/toolClosed.
  2. Split Spec into pure metadata/recipe vs content builder; relocate docking ownership so content-by-toolId (not the opening frame) is the durable unit under docking.
  3. Introduce a Shortcut model (id, actionRef, x, y, label, iconKey) separate from VShortcut view.
  4. Unify IDs (toolId everywhere; dockables derive from toolId).
  5. Only then expand DockingState and drop the dummy observed JList / desktopmgr legacy path.
