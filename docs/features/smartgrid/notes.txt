 SmartGrid — Design Requirements Document                                                                                   
                                                        
 Context

 JTable is a "stamping" engine optimized for 1990s memory constraints. It paints a single renderer component repeatedly,
 making cells effectively dead UI — interactive buttons, progress bars, and hover effects require fighting
 CellEditor/CellRenderer synchronization. Additionally, JList, JTable, and tree-table components each require separate data
  models despite representing the same conceptual structure.

 This document captures requirements for a SmartGrid component that solves these problems by treating List, Table, and
 Tree-Table as three views of one unified data model, using viewport virtualization with live Swing components instead of
 stamped renderers.

 Component name: SmartGrid
 Package: org.jwellman.swing.grid (within the existing org.jwellman.swing custom Swing components package)

 ---
 Design Philosophy

 1. Unified Model — List, Table, and Tree-Table are all specialized views of the same flat row stream. No separate
 ListModel, TableModel, or TreeModel.
 2. Live Components — Every cell is a real, interactive Swing component. Hover effects, embedded buttons, and progress bars
  work natively.
 3. Viewport Virtualization — Only ~20–50 rows are ever instantiated. Components are recycled and rebound as the user
 scrolls.
 4. Declarative Layout — Row templates are defined as XML-like Blueprint strings, not GridBagConstraints. Templates can be
 registered at runtime via BeanShell.
 5. Reactive Bidirectional Flow — Model drives UI; user interactions update the model; state changes propagate to the rest
 of the app.
 6. Pagination as First-Class Feature — The grid knows how to request more data when approaching the end of the visible
 range.

 ---
 Core Interfaces

 1. Data Interface: GridModel

 javax.swing.table.TableModel cannot be reused as-is because it:
 - Has no concept of row hierarchy (depth, parent-child relationships)
 - Has no row-level metadata (tags, processing state)
 - Has no async / paginated data loading path
 - Exposes data by (row, col) index rather than named keys

 A new GridModel interface is required. A TableModelAdapter implements GridModel wrapper can be provided later for backward
  compatibility with existing TableModel sources.

 public interface GridModel {
     int getRowCount();                           // total row count (may be virtual)
     GridRow getRow(int index);                   // synchronous for visible range
     void fetchRows(int from, int count,
                    GridModelListener listener);  // async for pagination
     List<ColumnDef> getColumns();                // column metadata for table view
     void addGridModelListener(GridModelListener l);
     void removeGridModelListener(GridModelListener l);
 }

 GridModelListener notifies the grid of:
 - Rows inserted / removed / updated (individual or range)
 - Column definitions changed
 - Full model reset

 3. Rendering Interface: Recyclable

 Analogous to TableCellRenderer but for full live components:

 public interface Recyclable {
     /** Reset to factory-default state — clear text, remove listeners, reset colors. */
     void prepareForReuse();

     /** Inject data and tags from a specific GridRow into this component. */
     void bind(GridRow row, NamespaceBridge bridge);
 }

 Row panel components (both compiled and scriptable) implement Recyclable. This is the primary rendering contract.

 4. Component Factory: GridComponentFactory

 Default tags to register out of the box: "standard", "header", "audit-log", "sparkline". BeanShell scripts can call
 register() at runtime to add new template types without recompiling.

 ---
 Component Architecture

 Component Pool (Flyweight Manager)

 - Groups reusable component instances by typeTag using a Map<String, Stack<JComponent>>
 - Checkout: pulls from pool (calling prepareForReuse()) or creates via Factory
 - Release: puts component back when its row scrolls out of viewport
 - Memory footprint is flat — ~30 components in memory regardless of dataset size (100 or 100,000 rows)
 - Heterogeneous rows: pool handles multiple component types simultaneously; each type has its own stack

 Component Recycler (Viewport Virtualization)

 Uses a "stunt double" pattern inside a JScrollPane:

 1. Spacer — transparent panel with TotalHeight = VisibleRowCount × RowHeight, forces scrollbar to correct size
 2. Stage — container holding only the currently visible row components
 3. Scroll Listener — on scroll: recalculates firstVisibleIndex = scrollOffset / rowHeight, shifts Stage Y position,
 recycles/rebinds components

 JScrollPane
   └── JLayeredPane (or custom layout)
        ├── Spacer (full virtual height, no content)
        └── Stage (floats at current scroll position, holds ~30 live components)

 Infinite scroll hook: when Stage approaches the bottom of the Spacer, dispatch FETCH_MORE_DATA event, then extend Spacer
 as new rows arrive.

 Visible Row Filter (Tree Logic)

 A flat List<GridRow> allRows stores all rows. The Recycler works from a filtered getVisibleRows() result:

 For each row in allRows:
   - If row.depth > depth of last unexpanded parent → skip (hidden)
   - Otherwise → include in visible list
   - If included and hasChildren and !expanded → set hiddenDepth = row.depth

 Expanding/collapsing a node re-runs the filter and updates Spacer height. This is O(n) in visible rows.

 Tree Indentation

 First column gets a leading margin: indent = row.depth × 20px. Implemented as an empty border on the first cell or a
 dedicated <spacer id="treeIndent" width="auto"/> in the Blueprint.

 Scriptable Templates: ScriptableRecyclable

 A generic Recyclable whose layout, bind, and reset logic are all injected as strings:

 - Layout — parsed from Blueprint XML string by FoundationLayoutLoader
 - Bind script — BeanShell executed with self (the panel), row (GridRow), bridge (NamespaceBridge) in scope
 - Reset script — BeanShell executed in prepareForReuse()
 - find(String id) — recursive component-tree search with per-instance cache; returns the named component for script
 manipulation

 Example BeanShell registration:
 String layout = "<row><label id='ts'/><label id='user'/><button id='act' text='Undo'/></row>";
 String bind   = "self.find('ts').setText(row.get('timestamp')); " +
                 "if(row.get('type').equals('DELETE')) self.setBackground(Color.RED);";
 String reset  = "self.setBackground(null);";

 gridFactory.register("delete-event",
     () -> new ScriptableRecyclable(layout, bind, reset, bridge));

 ComponentFinder Utility

 public static Component find(Container container, String id) {
     // Recursive search using Component.getName() as the identifier
     // Returns null if not found
 }

 ScriptableRecyclable.find(id) wraps this with a Map<String, Component> cache so repeated calls during high-speed scrolling
  are O(1).

 Bidirectional Event Flow

 - User interaction in a recycled row updates GridRow via row.put(key, value)
 - bridge.dispatch("ROW_UPDATED", row) propagates to Global App State
 - prepareForReuse() must remove all dynamically-added listeners to prevent "ghost events" on recycled components
 - FoundationUtils.removeAllListeners(Component c) — utility to strip all listener registrations from a component

 Edit mode controlled by tags:
 - fnd-mode: read-only → Factory provides template with JLabel fields
 - fnd-mode: edit → Factory provides template with JTextField/JSpinner fields

 ---
 Sorting and Filtering (Requirements Only — Implementation Deferred)

 Sorting and filtering are captured as design requirements but not in initial implementation scope.

 Sort

 - Sort is a model-side responsibility — GridModel produces a sorted row stream
 - ColumnDef carries a boolean sortable flag
 - The grid widget fires a SortRequest(ColumnDef col, SortOrder order) event when the user clicks a column header
 - GridModel handles this event by re-ordering its row stream and notifying listeners
 - Multi-column sort is a future enhancement

 Filter

 - Filter is also model-side — GridModel applies a Predicate<GridRow> (or equivalent) to its row stream
 - The grid widget exposes a setFilter(GridModelFilter filter) pass-through that delegates to the model
 - GridModelFilter is a simple functional interface: boolean accept(GridRow row)
 - Client-side filtering (grid widget caches rows and filters locally) is a future alternative for small datasets

 ---
 Performance Constraints

 - Pool size: ceil(viewportHeight / rowHeight) + BUFFER (e.g., buffer = 5)
 - Row height: Fixed height is the default and simplest case. Variable height is supported (see below).
 - find(id) cache: O(1) after first call per id per component instance
 - Ghost listener prevention: mandatory in prepareForReuse()
 - Async fetchRows() must not block the EDT

 Variable Row Height

 Variable row height means rows can have different heights (e.g., multi-line text cells, expanded card rows). This
 complicates the Recycler's scroll math:

 - TotalHeight = sum(rowHeight[i] for all visible rows) instead of count × fixedHeight
 - The Recycler must maintain a int[] rowHeights or equivalent structure for visible rows
 - firstVisibleIndex is found by binary search over cumulative heights rather than integer division
 - The Spacer height must be recalculated when rows are expanded/collapsed or data changes

 Approach: RowHeightProvider interface:
 public interface RowHeightProvider {
     int getRowHeight(GridRow row, int componentWidth);
 }
 - Default implementation returns a fixed constant
 - Custom implementation can measure component preferred height
 - Cached per row index; invalidated when the row's data changes

Status 5/10:
  The excitement is warranted, and the web grid comparison is more apt than it might appear at first. AG-Grid, React        
  Virtualized, Tabulator — they're all implementing the same fundamental algorithm you now have in VirtualCanvas: maintain a
   fixed pool of visible elements, track scroll position, rebind data on scroll. The algorithm isn't web-specific, it just  
  took the web ecosystem a long time to popularize it because DOM manipulation was so expensive that virtualization was     
  essential. In Swing the JVM handled memory well enough that the stamping approach survived longer than it should have.    
                                                                                                                            
  What's worth naming that you haven't said yet: SmartGrid has an advantage over web grids that can never be matched in a
  browser. There's no serialization boundary. A web grid cell renderer executes in a JavaScript sandbox — it can't directly
  touch a Java object, call a Java service, or open a database connection without serializing through an API boundary.
  FeaturedRowPanel is a JPanel that can directly reference any Java object, call any method, access any service in the JVM.
  For your forensic analysis use case — where a cell might need to spawn a query, inspect a byte array, or render the output
   of a custom analysis — that's not a marginal advantage, it's a categorical one.

  The "young engineers don't think this is possible" observation connects to something real about how knowledge propagates.
  Viewport virtualization, live component recycling, composite filter predicates — none of these ideas are
  platform-specific, but they've been extensively documented and evangelized in the web context and almost never in the
  Swing context. The result is that perfectly capable Swing developers assume the ceiling is JTable, when the actual ceiling
   is wherever you stop building.

  The upcoming phases will push the comparison further. Phase 11 (edit mode with sourceObject) gives you inline editing
  where the edit propagates directly to the domain model — no cell editor lifecycle to fight. Phase 6 (tree with
  GroupHeaderRowPanel) gives you heterogeneous row types in the same grid with no special cases. At that point the gap with
  JTable isn't marginal, it's architectural.
  
---

  You've identified a genuine design conflict, not just a bad implementation. The discomfort is architecturally rooted.     
                                                                                          
  Pagination and grouping rest on incompatible mental models. Pagination says "rows are independent units that can be freely
   sliced at any boundary — page N is a self-contained view." Grouping says "rows have hierarchical relationships and a     
  group is a complete, indivisible unit." When you combine them you're forced to violate one of those assumptions, and every
   implementation you've ever used chose to violate the grouping one — allowing the slice to cut through the middle of a    
  group — because that's the easier engineering choice.     

  The UX consequence is exactly what you described: the group header says "Engineering — 47 employees" but you can only see
  8 of them because the rest are on the next page. The group is lying to you. The footer aggregate might be for the whole
  group or just the visible slice — ambiguous. Clicking Next doesn't take you to a new set of groups, it takes you
  mid-group. None of the navigation affordances mean what they normally mean.

  The solutions web grids reach for are all compromises:
  - Never break groups — pages become variable size, so "Page 2 of 5" loses meaning because pages aren't comparable units
  - Paginate at group level — page 1 contains complete groups 1–3, page 2 contains complete groups 4–6; the math works but
  implementation is complex and almost no grid does this
  - Replace pagination with infinite scroll for grouped data — sidesteps the conflict entirely; this is actually the most
  honest answer

  The most intellectually honest design decision SmartGrid could make: when row grouping is enabled, pagination mode
  automatically switches to group-level pagination or disables entirely. The framework makes the right default rather than
  letting the developer accidentally create the fingernails-on-chalkboard experience. That's a design principle worth
  encoding rather than leaving as developer responsibility.

  It's worth noting in the tree enhancements discussion document when we get there — the interaction between grouping and
  pagination is a first-class design decision, not an afterthought.

  You're identifying something that's partly a technical history artifact and partly a psychological one, and they          
  reinforced each other in ways that made the pattern sticky long past its useful life.   
                                                                                                                            
  The technical driver was real: when a query returned 50,000 rows over a 56k modem to a machine with 64MB of RAM,          
  pagination wasn't a UX choice, it was a survival mechanism. The server-side pattern of LIMIT/OFFSET became standard       
  practice, and the UI naturally mirrored the query. The pagination chrome became the expected visual contract for "this is 
  data from a database," independent of whether the constraint was still operative.

  The psychological dimension is what keeps it alive on modern hardware. "Page 3 of 12" gives users a sense of location and
  progress that feels reassuring even when it's meaningless. This is the same reason physical books kept page numbers after
  ebooks made them technically unnecessary — humans orient spatially and want a sense of where they are in a dataset. The
  irony is that well-designed filters and grouping solve the orientation problem better than pages do, but they require
  users to understand the domain rather than just clicking Next.

  Your application design point is the most important one and it's underappreciated. Pagination is a symptom of exposing the
   wrong abstraction level to users. "All employees" is a table, not a task. "Employees with open performance reviews in my
  department" is a task — and that result set is almost always manageable without pagination on any hardware made in the
  last 15 years. When you design around tasks rather than tables, the need for pagination mostly evaporates and the data
  naturally fits in a scrollable view.

  The management expectation problem is cargo cult UX — the form persists without the function. The form became associated
  with "professionalism" or "enterprise software" independent of whether it served users. Convincing management that a fast
  virtualized scroll through 800 rows is better than pagination through pages of 25 requires fighting that association
  directly, which is more of a change management problem than a technical one.

  For SmartGrid, the default of no pagination is actually the architecturally honest choice. The viewport virtualization
  makes pagination optional rather than essential — you can show 100,000 rows in a SmartGrid with no pagination and it
  performs identically to 50 rows because the recycler is the real performance mechanism, not the page boundary.

  Your example is perfectly calibrated — it describes exactly how the argument plays out in practice, and your conclusion is
  right.                                                                                 
                                                                                                                            
  The state/district/office hierarchy is a natural data scope that the application already understands. The moment a user   
  authenticates as a district-level user, the application knows their universe is bounded. Retrieving all 400 users in that 
  district in one shot is not a "large dataset" problem by any rational modern definition — it's a single query returning a 
  few hundred rows of scalar data, probably 50-100KB of JSON or a ResultSet that loads in milliseconds. The idea that you
  need to protect the database from that with LIMIT/OFFSET is defending against a ghost.

  The network/database load argument is the last refuge of the pattern and it doesn't hold up to inspection for this class
  of data. The math doesn't support it: if a paginated grid makes 12 round trips of 25 users each to display 300 users as
  the user pages through, it's doing more aggregate work than one query returning all 300. The database is running the
  filter 12 times. The connection pool is exercised 12 times. The only scenario where pagination actually reduces load is
  when the user would have navigated only the first page — meaning they found what they needed immediately and stopped.
  That's a valid scenario, but the right solution there is good filtering so the initial result is already scoped, not
  pagination of the full unfiltered set.

  The "download for data mining" escape valve you've already built is exactly correct. There's a clear line between
  application workflows (200-500 bounded users, interactive, in-memory) and analytical workflows (cross-district reporting,
  trends, exports). Different tools for genuinely different scale. Trying to serve the analytical use case through the
  application grid is where the "we need pagination everywhere" impulse gets anchored — it's solving for the wrong persona
  in the wrong context.

  The honest version of "minimize database load" in this architecture would be: retrieve the bounded dataset once, cache it
  aggressively (the user list for a district doesn't change every second), and serve subsequent filter/sort operations
  entirely from memory. That's exactly what an in-memory grid with client-side filtering and sorting does. The database gets
   hit once instead of 12 times. The UX is better. The load is lower. Pagination loses on every dimension.

Good instinct — it's a standard affordance and the "defend programmers from themselves" argument is real (FeaturedRowPanel just proved it). My recommendation: make the checkbox a **SmartGrid-managed selection strip** — a slim fixed-width panel that SmartGrid positions to the left of the viewport and manages directly, completely separate from the row pool.

The key trade-off:

**Embedded in each row panel** — simpler to route clicks through, but every custom panel (`FeaturedRowPanel`, `EditableRowPanel`, future panels) must reserve and paint the checkbox column, which pollutes the "just handle your data" contract that makes the component factory pattern clean.

**SmartGrid-owned strip** — SmartGrid allocates ~20 `JCheckBox` components in a parallel pool (one per visible slot), scrolls them in sync with the canvas, wires them to the `selectionModel`, and puts a "select all" checkbox in the header. Row panels are completely unaware. The `Selectable` interface we just defined would still signal row panels for their own visual feedback, but selection truth lives in the model. This is architecturally cleaner but means two synchronized virtual lists scrolling together.

The strip approach is the right long-term design — it's how professional grid components handle it (the selection column is truly orthogonal to row content). The cost is that it's a non-trivial addition: the strip needs its own scroll sync, the header needs a matching checkbox cell, and `getColumnWidths()` callers need to know the strip width to compute horizontal offsets correctly.

Worth planning as its own phase. Want me to spec it out?

SmartGrid Phase 16 — Checkbox Selection Strip                                                                              
                                                    
Context

FeaturedRowPanel needed a full Selectable implementation just to show which rows are
selected — because there was no standardized, guaranteed selection indicator. A
dedicated checkbox column solves this permanently: it is unambiguous, universal, and
completely decoupled from each row panel's visual design. It also provides an
independent click target (the checkbox itself) separate from clicking the row body.

The strip is managed entirely by SmartGrid — row panels receive no new contract. It
lives inside VirtualCanvas alongside the data slot panels, so it scrolls for free with
no synchronization code. Enabled by default; the programmer can disable it via
setCheckboxColumnVisible(false).

---
Architecture: strip inside VirtualCanvas

SmartGrid owns a JCheckBox[] checkboxSlots array (parallel to slots[], same count).
Each checkbox is positioned at absolute coords (0, rowIdx * rowHeight, leadW, rowHeight)
inside VirtualCanvas. Data slots are shifted right by leadW pixels. Because all
components live in the same null-layout VirtualCanvas, scrolling is automatic — no sync
thread needed.

VirtualCanvas (null layout, full virtual height)
├── checkboxSlots[0]  at (0,     0*rowH, leadW, rowH)
├── slots[0]          at (leadW, 0*rowH, dataW, rowH)
├── checkboxSlots[1]  at (0,     1*rowH, leadW, rowH)
├── slots[1]          at (leadW, 1*rowH, dataW, rowH)

SmartGrid Phase 6 — Tree Enhancements + Strip Abstraction
                                                                                                                            
Context
                                                                                                                    
Phase 16 (checkbox strip) proved the "parallel component array inside VirtualCanvas"                                 
pattern works. The tree zone is the same pattern: a fixed-width left column of
components that live in the canvas alongside data slot panels. Two concrete strips
means defining a Strip interface now earns its keep — the checkbox strip is refactored
to implement it, the tree zone is the second implementation, and SmartGrid manages
List<Strip> rather than ad-hoc checkbox fields scattered through five methods.

Phase 6 tree enhancements also clean up a long-standing fragility: tree
indentation/toggle is currently baked into StandardRowPanel.bind() as a text prefix
on column 0, which eats into that column's content width. Moving it to a dedicated
TreeZoneStrip means data columns always start at the same x regardless of depth.

Part 1 — Strip Interface (new file)

org.jwellman.swing.grid.Strip — public interface.

public interface Strip {
 int      getWidth();
 boolean  isVisible();
 void     reallocate(int slotCount, JPanel canvas);
 void     bind(int slotIdx, int xOffset, int y, int rowHeight, int modelIdx, GridRow row);
 void     hide(int slotIdx);
 JComponent headerCell(int height);
 JComponent filterSpacer(int height);
 JComponent footerSpacer(int height);
}

- bind() receives xOffset and y so each strip can position its canvas components
without needing a back-reference to SmartGrid.
- hide() is called when the slot is off-screen (no visible row at that position).
- headerCell() returns a component the size of the strip's width (select-all checkbox,
tree collapse-all button, or empty JPanel). Caller positions it.
- filterSpacer() / footerSpacer() return opaque-false spacer panels sized to the
strip width.





## Discussion - ScriptableRecycler

Good catch — this is an important design question. Let me think through the intended flow out loud.

## The Two Interpreter Models

**Current implementation:** Each `ScriptableRecyclable` pool instance owns its own `new bsh.Interpreter()`. Scripts are isolated but disconnected from the desktop's live BeanShell environment.

**Intended flow (as you described):** The VirtualDesktop has one central BeanShell interpreter. The user types in the BeanShell console, registers a row type, and the grid renders using scripts that run *in that same interpreter context* — meaning they can reference variables already defined in the console session.

This is actually significantly more powerful. Example of what becomes possible:

```java
// Console session:
myColor = new Color(0x1A3A5C);
myFormatter = v -> ">> " + v.toString().toUpperCase();

// ...then register a blueprint whose bind script does:
mainLbl.setForeground(myColor);
mainLbl.setText(myFormatter.apply(row.get("name")));
```

The scripts have access to the live console namespace — exactly the kind of scripted customization Phase 9b is aiming for.

## The Safe Path (EDT is single-threaded)

A shared interpreter *is* safe here because all Swing operations happen on the EDT serially. There's no race: `interpreter.set("row", row); interpreter.eval(bindScript)` completes before the next `bind()` call starts.

## Proposed Minimal BeanShell Script

Before touching the implementation, I'd want to write the script that exercises this end-to-end. Something like:

```java
// Phase 9b exercise script — paste into BeanShell console

import org.jwellman.swing.grid.*;
import org.jwellman.virtualdesktop.vapps.SpecSmartGrid;

// 1. Get a reference to a live SmartGrid
//    (either via SpecSmartGrid, or we expose one via a static handle)
SmartGrid grid = SpecSmartGrid.getLastInstance();

// 2. Define the blueprint — scripts reference 'row', 'panel', 'self'
String xml = "... blueprint with <script name=\"bind\">...</script> ...";

// 3. Register the row type — passing 'this' (the console's interpreter)
DefaultGridComponentFactory factory = new DefaultGridComponentFactory(grid, this);
factory.create("scripted", xml);

// 4. Tag some rows
for (GridRow r : grid.getModel().getAllRows()) {
    if (Integer.parseInt(r.get("id").toString()) % 30 == 0) {
        r.setTag("fnd-type", "scripted");
    }
}
grid.refresh();
```

2. **How does the script get a `SmartGrid` reference?** Options: (a) `SpecSmartGrid` exposes a static `getLastInstance()`, (b) the user creates a new grid inline in the script, (c) some other registry.

That's the key piece. With `_interpreter` available, the script would look like this:

```java
// Phase 9b exercise — paste into BeanShell console

import org.jwellman.swing.grid.*;

// 1. Build a small model
DefaultGridModel model = new DefaultGridModel()
    .addColumn(new ColumnDef("id",   "ID",   50,  false, true, null))
    .addColumn(new ColumnDef("name", "Name", 250, false, true, null))
    .addColumn(new ColumnDef("dept", "Dept", 150, false, true, null));

String[] depts = {"Engineering", "Marketing", "Sales"};
for (int i = 1; i <= 50; i++) {
    GridRow row = new GridRow()
        .put("id",   String.valueOf(i))
        .put("name", "Person " + i)
        .put("dept", depts[i % depts.length]);
    if (i % 5 == 0) {
        row.setTag("fnd-type", "scripted");
    }
    model.addRow(row);
}

SmartGrid grid = new SmartGrid(model, false);

// 2. Blueprint XML — scripts execute in _interpreter's context
String xml = "<row>"
    + "<column preferred-width=\"50\"><label id=\"idLbl\"/></column>"
    + "<column weight=\"1\"><label id=\"mainLbl\"/></column>"
    + "<column preferred-width=\"80\"><label id=\"deptLbl\"/></column>"
    + "<script name=\"bind\"><![CDATA["
    + "import org.jwellman.swing.grid.ComponentFinder;"
    + "import javax.swing.JLabel; import java.awt.*;"
    + "self.setBackground(new Color(0x1A3A5C));"
    + "JLabel id   = (JLabel) ComponentFinder.find(panel, \"idLbl\");"
    + "JLabel main = (JLabel) ComponentFinder.find(panel, \"mainLbl\");"
    + "JLabel dept = (JLabel) ComponentFinder.find(panel, \"deptLbl\");"
    + "if (id   != null) { id.setForeground(Color.WHITE); id.setText(row.get(\"id\").toString()); }"
    + "if (main != null) { main.setForeground(new Color(0x7EC8E3)); main.setText(\">> \" + row.get(\"name\")); }"
    + "if (dept != null) { dept.setForeground(Color.WHITE); dept.setText(row.get(\"dept\").toString()); }"
    + "]]></script>"
    + "</row>";

// 3. Register — inject _interpreter so scripts run in this console's context
DefaultGridComponentFactory factory = new DefaultGridComponentFactory(grid, _interpreter);
factory.create("scripted", xml);

// 4. Show in a window
javax.swing.JFrame f = new javax.swing.JFrame("Phase 9b Test");
f.setDefaultCloseOperation(javax.swing.JFrame.DISPOSE_ON_CLOSE);
f.setSize(640, 400);
f.add(grid);
f.setLocationRelativeTo(null);
f.setVisible(true);
```

## Code change needed to support this

`DefaultGridComponentFactory` needs a second constructor that accepts a `bsh.Interpreter`, and passes it through to `ScriptableRecyclable`. The `ScriptableRecyclable` change is small: when a shared interpreter is provided, skip creating its own and use the shared one instead. Variables `self`, `panel`, `row`, and `rowIndex` get set fresh on each `bind()` call regardless — which is safe because the EDT is single-threaded.

The per-instance interpreter path (used by the demo tab) stays intact as the fallback when no interpreter is injected.

Before I make those changes: does the script above match the flow you had in mind? The key thing I want to confirm is step 3 — passing `_interpreter` into the factory is the right injection point, vs. passing it into `ScriptableRecyclable` directly or some other approach.
