The invariant (your AppSpec insight)

A tool is defined by how it is launched and by at least one JPanel (or JComponent) the environment hosts. External apps still fit: the OS process is a side effect of LaunchAware; the desktop still creates and manages a panel for that launch. Views never invent tools — they ask ToolService / the store.

Aligned with existing docs

This matches REQUIREMENTS.md “view substitutability” and DESKTOP.md’s planned DesktopState → DesktopController → pure VShortcut path. Taskbar remains the reference implementation of the pattern.

1. Theoretical contracts

Names below are target vocabulary. “Existing anchor” is what to evolve or keep rather than invent from scratch.

Contract Role Minimum surface Existing anchor
ToolDefinition Catalog entry: what can be launched id, title, iconKey(s), className, attrs, flags VappConfig + DesktopShortcut + ExternalAppConfig
ToolCatalog Queryable set of definitions list / findById / byMenuGroup ActionFactory (static list) — not a real catalog API
ToolSpec Launch recipe + exposed content title, icon, getContent(): JPanel, optional configure/launch VirtualAppSpec (closest ancestor of the idea)
ToolInstance One running tool id, definitionId/type, title, frameState, … ToolInstance (state.model) — keep
ToolService Lifecycle operations (mutations) open / close / activate / minimize / restore DesktopManager methods — concrete, not an interface
ToolWindow Host chrome for content (temporary placement) toolId, setContent, show/hide; content may move to another host under docking VirtualAppFrame — is a JInternalFrame today; not the durable identity of the tool
DesktopState + Shortcut Shortcut placements on the surface shortcutId → defId, x, y, label, icon DesktopShortcut DTO only; DESKTOP.md names DesktopState
DesktopView Renders desktop surface (shortcuts ± wallpaper) setShortcuts / listener for open/move/select Missing — VDesktopPane + VShortcut are ad hoc
WindowListView Renders open-tools list (taskbar zone) setItems / setSelectedId / listener WindowListView — keep (reference pattern)
ToolBrowserView (optional) Renders catalog ± open status definitions + which ids are open Missing — menus approximate this poorly

Layering (who talks to whom)

Catalog: ToolDefinition → ToolCatalog (load from JSON; no Swing)

Recipe: ToolCatalog.open(defId) → instantiate ToolSpec → optional Configurable / LaunchAware

Runtime: ToolService assigns ToolInstance id, asks ToolWindow host for chrome, puts Spec.getContent() inside, dispatches store updates

Views: subscribe to AppStore (and/or catalog); emit intents via listeners; never hold the live frame list as authority

Docking (fundamental): Every open tool’s content is a dockable unit; hosts (frames/workspaces) are temporary placement. Single-host-for-life is the special case that may look like “no docking.” Dockable identity keyed by toolId; SPI stays; Spec does not own the service. Close disposes content wherever it lives, not necessarily the opening frame.

2. Views as realizations of the same model

View contract Reads Writes via Example realization
DesktopView DesktopState (shortcuts) open tool, move/select shortcut VDesktopPane + VShortcut tiles
WindowListView ToolsState ∩ WindowListState (open tools) activate / close / group UX SmartGridWindowListView, JListWindowListView
ToolBrowserView ToolCatalog ⊕ open ToolInstance ids launch / focus if already open Tools menu today; could be palette, dock, grid
ToolWindow (frame chrome) current host for one ToolInstance’s content close / minimize / focus (via ToolService) — close targets content-by-toolId when docking moves panels VirtualAppFrame on VDesktopPane (temporary host)
Toolbar is not one thing

A taskbar that shows only open tools is a WindowListView over ToolsState. A launcher that shows all available tools and whether each is open is a ToolBrowserView over ToolCatalog ⊕ ToolsState. Same paradigm; different projections. Menus are just another ToolBrowserView.

What “Met” means for ToolSpec

Keep the mental model of VirtualAppSpec: definition of launch + one hosted panel. Refactor toward an interface roughly like:

String getTitle(); Icon getIcon(); JPanel getContent();

plus optional Configurable / LaunchAware

Move off Spec: DockingWorkspace, static DockingService, global dockable ID set, InternalFrameProvider as a rare host strategy — not part of the core ToolSpec contract

5. Implementation order (gaps only)

  1. Extract ToolDefinition + ToolCatalog from ActionFactory/JSON — Actions become adapters that call ToolService.open(defId).
  2. Declare ToolService; make DesktopManager the first implementation still creating VirtualAppFrames, but all views call the interface.
  3. Narrow VirtualAppSpec toward ToolSpec (content + metadata only); relocate docking session to toolId-scoped owner. Treat docking as fundamental: hosts are temporary; a content realizer (toolId → panel/dockable) supports close wherever the panel currently lives.
  4. Put iconKey (and definitionId) on ToolInstance; delete WindowListController.frameCache.
  5. DesktopState + DesktopView + pure VShortcut (DESKTOP.md) — same pattern as taskbar.
  6. Only then: AppStore as sole open-tool registry; frames list becomes a realizer cache, not authority.
Edge case that stays true

ExternalAppSpec: ToolSpec.getContent() still returns a managed panel; LaunchAware.launch() starts the OS process. The paradigm does not require “all UI is in-process” — only that the desktop always hosts ≥1 panel per open ToolInstance.

Docking: fundamental, with a “no docking” special case

For this product, every open tool’s content is a dockable unit; frames/workspaces are temporary hosts. A tool that never leaves its opening container is just the degenerate special case — it may look like classic one-window-per-tool UI, but close/move still mean content-by-toolId, not “whatever frame opened this.”
